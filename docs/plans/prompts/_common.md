# Rules for every fired prompt

Read this before doing anything else. The item's own file adds to it and never relaxes it.

## Context to load
- The item's section in `docs/plans/implement-queue.md` (I-items) or `docs/plans/deep-search-queue.md` (DS-items).
- Every finding of `docs/plans/coverage-audit.md` that the item cites.
- Anything else, only when the item names it.

## Git
- Start from `plans-2026-10-24`, not `main`: waves 1 and 2 are merged only there. Then create the branch named in the item (`git switch -c <branch>`).
- Commit on that branch when the item's "Done when" holds, with a message that states the result.
- Do not push, merge or open a PR. The owner does that.

## Never
- Never write to `research/n3/<domain>/`, `research/results_manifest.json`, `residual/frozen/`, `instrument/`, `sessions/` or any `.env`.
- New outputs go to the directory the item names.
- `residual/src/residual/{vocab,provenance,claims,ledger,gates,residual}.py` are in the frozen semantics hash. Add new modules instead of editing them, unless the item says a re-freeze is intended.
- Never read gold contents (CTA task lists, cue lists) before a pre-registration is hash-committed. Check gold by metadata and author contact only.
- Never print, display or open sealed or encrypted material.

## Before changing a rule
Before you change any parser, filter, gate or admissibility rule, replay the new rule on the committed artefacts. Report how many records it flips, and which downstream sample it shrinks or empties. Do this before you keep the change.

## Gates and controls (L7.3)
A gate, control or decision rule you build is used only after you show it can discriminate:
1. Compute its best reachable outcome from the observed baseline.
2. Run it on a planted positive, which must fire.
3. Run it on a trivial stand-in (noise, length, a surface statistic), which must not pass.
4. A control applies the same exclusions to both arms. Its conclusion names only the variable the arms differ on (L7.4).

## Judges and parallel arms
- Every run judged or generated by a cheap model (local qwen, a small hosted model) gets a parallel top-tier arm on the same inputs, with a hard `--max-usd`. Report both arms; the cheap arm alone never settles a decision. A cached top-tier run counts as that arm only if it was judged on the same pairs (equal `pairs_sha256` in `control2.json`; replay it offline to add the field if it predates it).
- ADR 0009: a judge from the ledgers' generator or verifier family (OpenAI, Anthropic) runs only beside an other-family arm on the same pairs, prompt and parser. Run the other-family arm first and pass its `control2.json` as `--parallel-arm`; a reading counts only where both arms agree in direction.
- A judge becomes a guard or a counted arm only after it passes the real-judge L7.3 check on the same control (`research/n3_control_v3/l73.py`), in two runs with identical results. Luna passed once and failed the retest on identical prompts (`research/n3_control_v3/RESULT.md`). "Identical" means the same verdict and the same states the rule reads, with at least 90% of individual judgements equal, because hosted models are not bitwise deterministic at temperature 0 (owner, 2026-10-27, post hoc after gemma's G1 retest: 71 of 76 equal; `research/closure_topicality/RESULT.md`).
- Say what a judge contrast is: the whole judge (model, serving, decoding), never family alone (L7.4).

## Paid calls (L7.1, L7.2)
- Run `python3 scripts/key_headroom.py` first.
- Give every live command a hard `--max-usd`.
- The sum of this item's caps must not exceed the headroom. If it would, stop and ask.
- No live call ever runs inside a test.

## Tests
- Work test-first (`superpowers:test-driven-development`).
- The package suite must pass:
  - `uv run --directory residual pytest -q`
  - `uv run --directory reconstruct pytest -q`
  - `uv run --directory gapmap pytest -q`
- The PostToolUse hooks rerun them after edits; a failing suite blocks "done".

## Owner decisions
When the item names an owner decision, stop at that point and ask with `AskUserQuestion`:
- Order the options by technical merit.
- Mark exactly one option "(Recommended)" and give the evidence for it.
- Never pick on the owner's behalf.

## Synthetic material
Anything generated from a specification is labelled `SYNTHETIC`, with its spec hash, and stored apart. It may debug a pipeline, but it is never a criterion and never feeds a gate.

## Mistakes
The moment a mistake is caught, record it with the `lessons` skill (definition of done).

## Reviews
- Before you register or hash-commit any pre-registration, run `methods-critic` on it.
- Run `citation-verifier` on every note written under `research/`.
- Run `validity-reviewer` if anything near `instrument/` is touched (it should not be).

## Finish
1. Write the item's result note at the path the item names. It opens with a three-line card, then the result and the decision it feeds (continue / change / stop, or the threshold it informs):
   - **Question:** one sentence.
   - **Answer:** one sentence, with its number and interval.
   - **Changed:** what the plan does differently because of it.
   
   Next to the note, write `report.json` for the wave report (the owner reads pictures first; wave 1's text had to be rebuilt by hand):
   ```json
   {"item": "I5", "card": {"question": "…", "answer": "…", "changed": "…"},
    "worked": "one line, ≤ 20 words, with its number, or null",
    "failed": "one line, ≤ 20 words, with its number, or null",
    "figure": {"title": "the finding, with its number", "kind": "bar | dot-and-interval | line | flow | table",
               "rows": [{"…": "…"}], "reference": "the line or mark the rows are checked against, with its value",
               "source": "committed file and field the rows come from"}}
   ```
   Every number in `rows` is read from a committed file named in `source`, never retyped from memory. One figure, unless the item feeds two decisions. A negative result is a `failed` line, not a footnote.
2. Add one status line under the item's heading in `docs/plans/implement-queue.md` or `deep-search-queue.md`: date, result, note path, commit.
3. Update `PROGRESS.md` only if a NOW item's status changes.
4. Reply to the owner in two to five sentences: the result, the decision it feeds, what is unblocked, and any owner decision now due.

## Wave report
The session that finishes a wave's last item builds the wave report, to wave 2's level (https://claude.ai/artifact/M1NDPick23TyXjJ1gPQis1).
1. List the wave's items from `README.md` § Waves. An item with no prompt, or whose "Needs first" is unmet, counts as not run. For every other item, check its branch for a committed `report.json` (`git show <branch>:<path>`). If one is missing, name it in your reply and stop; the next item to finish checks again. If `git log --all --grep "Wave <N> report"` finds a commit, the report exists: stop.
2. Ask Codex (`gpt-5.6-sol`, effort high, read-only) for a storyboard from those files, using `wave-report-storyboard.md`.
3. Build it as a new Claude Docs report. It has:
   - a verdict line;
   - "Wave <N> at a glance" (worked / failed);
   - the decision path;
   - one section per decision, with a figure and a Question/Answer/Changed card;
   - the decisions taken;
   - what the next wave must settle.

   Put the full notes in a second tab. Screenshot every figure before publishing it.
4. Ask Codex to review the built report against the sources, and apply every fix you verify.
5. Save the link in `PROGRESS.md` and `docs/plans/implement-queue.md` on your branch and commit, with a message starting "Wave <N> report".
6. Reply with:
   - one line per item (result, decision, branch, commit), with the not-run items named;
   - the report link;
   - the next wave's unblocked prompts, as copy-paste lines.
